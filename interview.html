Module 09 · Interview Bank

Turn knowledge into a calm, structured answer.

In live SQL, communicate the grain, assumptions and validation before chasing syntax. In business rounds, connect the metric to a decision.

Rapid-fire theoryLive SQLCasesDebugging

Rapid-fire answers

QuestionStrong compact answer
WHERE vs HAVING?WHERE filters rows before grouping; HAVING filters groups after aggregation.
DELETE vs TRUNCATE vs DROP?DELETE removes chosen rows; TRUNCATE removes all rows efficiently; DROP removes the object definition.
PRIMARY KEY vs UNIQUE?Both enforce uniqueness; the primary key is the row’s main identity and cannot be NULL. MySQL permits multiple UNIQUE constraints.
UNION vs UNION ALL?UNION removes duplicates; UNION ALL preserves them and avoids deduplication work.
CTE vs subquery?Both express intermediate logic. A CTE often makes multi-step queries clearer; neither is inherently faster.
RANK vs DENSE_RANK?Both preserve ties; RANK leaves gaps after ties, DENSE_RANK does not.
Why an index?It offers a cheaper access path for suitable reads, with storage and write-maintenance cost.
Why normalize?Reduce redundancy and insertion/update/deletion anomalies while protecting integrity.
What is ACID?Atomicity, consistency, isolation and durability—the core transaction guarantees.

Before writing: say this out loud

  1. “One output row should represent …”
  2. “I’ll assume ties should … and NULL means …”
  3. “I’ll filter to the relevant population, aggregate at …, then rank/join.”
  4. “I’ll validate row counts, duplicates and a small hand-calculated sample.”
This is senior analyst behaviorClarifying ambiguous requirements is part of the solution, not a delay before it.

Pattern 1: second-highest distinct salary

WITH ranked AS (
  SELECT employee_id, salary,
         DENSE_RANK() OVER (ORDER BY salary DESC) AS salary_rank
  FROM employees
  WHERE salary IS NOT NULL
)
SELECT employee_id, salary
FROM ranked
WHERE salary_rank = 2;

Ask whether the result should return every tied employee or one salary value.

Pattern 2: managers with at least five reports

SELECT m.employee_id, m.employee_name,
       COUNT(*) AS direct_reports
FROM employees e
JOIN employees m ON e.manager_id = m.employee_id
GROUP BY m.employee_id, m.employee_name
HAVING COUNT(*) >= 5;

Pattern 3: top three products in each category

WITH product_sales AS (
  SELECT p.category_id, oi.product_id,
         SUM(oi.quantity * oi.unit_price) AS revenue
  FROM order_items oi
  JOIN products p ON p.product_id = oi.product_id
  GROUP BY p.category_id, oi.product_id
), ranked AS (
  SELECT *, DENSE_RANK() OVER (
    PARTITION BY category_id ORDER BY revenue DESC
  ) AS rnk
  FROM product_sales
)
SELECT * FROM ranked WHERE rnk <= 3;

Confirm whether ties may return more than three rows; otherwise use ROW_NUMBER and a deterministic tie-breaker.

Pattern 4: find and inspect duplicates

SELECT email, COUNT(*) AS records
FROM customers
WHERE email IS NOT NULL
GROUP BY email
HAVING COUNT(*) > 1;

-- Keep the newest record in a review output
WITH tagged AS (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY email ORDER BY updated_at DESC, customer_id DESC
  ) AS rn
  FROM customers
)
SELECT * FROM tagged WHERE rn > 1;

Pattern 5: consecutive-day activity

WITH distinct_days AS (
  SELECT DISTINCT user_id, DATE(activity_at) AS activity_date
  FROM activity
), grouped AS (
  SELECT *, DATE_SUB(
    activity_date,
    INTERVAL ROW_NUMBER() OVER (
      PARTITION BY user_id ORDER BY activity_date
    ) DAY
  ) AS island_key
  FROM distinct_days
)
SELECT user_id, MIN(activity_date) AS streak_start,
       MAX(activity_date) AS streak_end, COUNT(*) AS streak_days
FROM grouped
GROUP BY user_id, island_key;

Debugging checklist

Correctness

  • Is the source grain what I think?
  • Did a one-to-many join multiply rows?
  • Can NULL remove or alter a row?
  • Is the denominator the correct population?

Boundaries

  • Are time zones and partial periods defined?
  • Are date ranges half-open?
  • Are ties deterministic?
  • Do zero-activity entities need to appear?

Validate with row counts before/after joins, uniqueness checks, min/max dates, null counts, totals against a trusted source, and 3–5 manually traced entities.

Business case answer: D-R-I-V-E

Define

Decision, stakeholder, scope and success metric.

Review

Data availability, grain, quality and assumptions.

Investigate

Segment, compare, form hypotheses and test drivers.

Validate

Reconcile, sensitivity-test and identify limitations.

Execute

Recommend owner, action, expected impact and monitoring.

ExampleIf conversion falls, segment by funnel step, channel, device, cohort and time; distinguish traffic-mix change from a product defect before recommending action.

Mock interview loop

  1. Pick one unseen SQL problem and set a 30-minute timer.
  2. Spend the first 3 minutes defining grain and edge cases.
  3. Write the solution while narrating, then test adversarial rows.
  4. Explain complexity/index opportunities in 60 seconds.
  5. Log the error pattern, not just the problem title.
