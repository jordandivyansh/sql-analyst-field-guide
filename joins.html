Module 03 · Relationships

Join at the right grain.

Most serious SQL mistakes are not syntax errors. They are silent row multiplication, missing matches, or the wrong relationship.

High-frequency interview topicCardinality first

Join types

JoinRows retainedTypical use
INNERMatching rows from both sidesOrders with valid customers
LEFTEvery left row, matching right rowsAll customers, including those with no orders
RIGHTEvery right rowUsually rewritten as LEFT for readability
FULL OUTERAll rows from both sidesReconciliation; not directly supported by MySQL
CROSSEvery possible combinationDate spine × product matrix
SELFA table joined to itselfEmployee-manager hierarchy

Core pattern

SELECT
  c.customer_id,
  c.customer_name,
  o.order_id,
  o.amount
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.customer_id;
ON vs WHERE with a LEFT JOINA right-table filter in WHERE removes unmatched NULL rows and can effectively turn the result into an INNER JOIN. Put match-specific conditions in ON when unmatched left rows must survive.
-- Keep every customer; attach only paid orders
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id
 AND o.status = 'paid'

Cardinality and duplicate multiplication

Before joining, ask whether each key is unique on each side.

One-to-one

One customer → one profile. Row count usually stays stable.

One-to-many

One customer → many orders. Customer data repeats by design.

Many-to-many

Many students ↔ many courses via a bridge table.

Danger: many-to-many by accident

Joining orders and payments only by customer can multiply both event sets.

-- Diagnose uniqueness before joining
SELECT customer_id, COUNT(*) AS rows_per_key
FROM customer_profiles
GROUP BY customer_id
HAVING COUNT(*) > 1;

Semi-join and anti-join

EXISTS: has a match

SELECT c.*
FROM customers c
WHERE EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.customer_id
);

NOT EXISTS: has no match

SELECT c.*
FROM customers c
WHERE NOT EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.customer_id
);

EXISTS tests presence without multiplying the outer row. It is usually clearer than joining and adding DISTINCT.

Self-join example

SELECT
  e.employee_name,
  m.employee_name AS manager_name
FROM employees e
LEFT JOIN employees m
  ON m.employee_id = e.manager_id;

Set operations

OperationDuplicate behaviourMySQL
UNIONRemoves duplicatesSupported
UNION ALLKeeps duplicates; usually fasterSupported
INTERSECTRows in both queriesUse INNER JOIN / EXISTS in MySQL
EXCEPTRows in first, not secondUse NOT EXISTS in MySQL
SELECT email FROM web_leads
UNION ALL
SELECT email FROM event_leads;

Set-operation branches must return the same number of columns in compatible types. The final column names come from the first query.
